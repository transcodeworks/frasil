# Frasil: guidance for coding agents

Frasil is an end-to-end encrypted collaboration framework with no central
authority. Each device keeps a replica. Devices exchange sealed, signed
units directly, through always-on peers, or both. This repository holds
protocol 1: its specification, a Rust implementation of it, the peer
service, and the browser package. Everything here is MIT.

Read `README.md` for the product. Read `docs/spec/README.md` and
`docs/spec/overview.md` before you change protocol behaviour.

## Where things live

| Path | What it is |
| --- | --- |
| `docs/spec/` | The normative specification, one document per area, `ext-*.md` for extensions. `rationale.md` is informative. |
| `docs/spec/reference/` | Python reference code written from the text. `generate.py` writes every vector file. |
| `docs/spec/vectors/` | Test vectors that every implementation must match byte for byte. They are generated, so never edit them by hand. |
| `crates/frasil` | The developer crate that applications depend on. Its root is the small API (`Device`, `Space`, documents, records, peers, admission). `frasil::advanced` exposes the engine, one call per spec procedure. `src/client/` holds the client. `examples/shared_note.rs` is the quick start. |
| `crates/frasil-*` | Protocol crates: one or more per spec document. They are internal and less stable than `frasil`. |
| `crates/frasil-index-derive` | `#[derive(Table)]` for the `index` feature of `frasil` (`frasil::index`), which re-exports it. A proc-macro must be a crate of its own; it is internal. |
| `crates/frasil-iroh` | The iroh binding: member connections, local discovery, pairing. |
| `crates/frasil-wasm`, `packages/frasil` | The browser package `@frasil/client`: wasm-bindgen bindings plus a TypeScript layer. |
| `crates/frasil-uniffi`, `bindings/` | Native bindings through UniFFI: the Swift package in `bindings/swift` and the Kotlin library in `bindings/kotlin`, generated by `scripts/bindings.sh`. |
| `apps/relay` | `frasil-relay`, the always-on peer. It runs HTTP/WebSocket and iroh, stores data in SQLite plus a directory or an S3 bucket, and can embed an optional iroh relay. |
| `tests/conformance` | Clients run against a live `frasil-relay`. Any test that needs a peer goes here. |
| `crates/frasil-testkit` | The vector loader (`vectors::VectorFile`, `hex`) and the claims check. It holds no peer. |
| `fuzz/`, `apps/relay/fuzz/` | cargo-fuzz targets for the protocol crates and for the peer's own records. Each directory is its own workspace. |
| `docs/*.md` | User guides: how it works, self-hosting, WebAssembly, links, lending a document, history, undo/versions/review, fuzzing. |

## The specification decides

- `docs/spec/` is the source of truth. Code follows the text. When code, a
  vector, and the reference code disagree, re-read the text. If the text is
  wrong or ambiguous, do not resolve it silently in code. Fix the spec, or
  report it and quote the text, the vector and the reference code.
- A behaviour change that touches the protocol starts in the spec. In the
  same change, update the text, then the reference code in
  `docs/spec/reference/`, then regenerate the vectors with `generate.py`,
  then update the Rust code. `generate.py --check` must pass, and
  `requirements.txt` pins the reference code's dependencies.
- Use the spec's names for types, fields, procedures and error classes.
  Check error verdicts in the order the spec's procedure states them.

## Invariants of the code

- Protocol crates hold no IO, clock or randomness of their own. Every random
  draw has a `_with` form that takes the bytes, so that vectors can drive
  it. Only `frasil-iroh`, the client driver in `crates/frasil`,
  `frasil-wasm` and `frasil-relay` do IO.
- A peer never judges an event's validity and never holds content keys. Do
  not add anything that would let a peer read, order or authorise.
- Extensions are Cargo features and are off by default. A crate declares
  only the features it implements. `frasil`'s `p1-full` turns on everything
  that crate implements. Feature-gated code must still build and pass with
  the default features alone and with `--all-features`.
- `frasil-relay` is the exception: it has no features, builds in every
  extension it implements, and turns each on at run time from
  `Settings::extensions` (`FRASIL_EXTENSIONS`). An extension that is off
  must behave as if it were absent: no service listed, its message types,
  mailbox kinds and routes answered as a core peer answers them, and none
  of its records read or written. Gate each entry point on the setting,
  not on a `cfg`. `tests/conformance` turns on, in its test peers, the
  extensions its features name (`frasil_conformance::settings`).
- Every vector family is claimed by exactly one crate in its `claims.txt`,
  one `<file.json> <family>` per line, or
  `[feature] <file.json> <family>` when only an extension proves it. The
  testkit's claims test fails on a family that is unclaimed, claimed twice,
  or does not exist.
- Every decoder of untrusted bytes has a fuzz target in a file of its own
  under `fuzz/`, or under `apps/relay/fuzz/` for the peer's records. A
  target that needs an extension lists it in `required-features`.
- The workspace lints apply everywhere: `missing_docs = "deny"`,
  `unsafe_code = "forbid"`, and Clippy with `-D warnings`. The edition is
  2024, and `rust-toolchain.toml` pins the toolchain.

## Dependencies

External crates are pinned to exact versions in the root `Cargo.toml`
under `[workspace.dependencies]`, with a comment on why each is there.
Crates use them with `workspace = true`. Adding or bumping a pin is a
change of its own, reviewed on its own: keep it out of feature PRs and
call it out. `cargo deny check` must pass. ring is the only TLS provider.

## Checks

Run the checks that cover what you touched. Use `-p <crate>` while you
iterate, then run the workspace commands that CI runs before you finish:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo clippy --workspace --exclude frasil-relay --exclude frasil-conformance --all-targets --locked -- -D warnings
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
node scripts/fetch-wycheproof.mjs            # once; frasil-crypto's Wycheproof test reads it
cargo test --workspace --locked
cargo test --workspace --all-features --locked
cargo deny check
```

Other checks, by area:

- Fuzz targets: `cargo fmt --manifest-path fuzz/Cargo.toml -- --check`
  (and the same for `apps/relay/fuzz/Cargo.toml`), and
  `scripts/fuzz.sh --build-only`, which needs nightly and cargo-fuzz.
- Features of `frasil`: `scripts/check-features.sh`, Clippy on the
  combinations an application might choose. Run it when you gate code on
  a feature.
- Tauri bridge: `scripts/check-tauri.sh`, when you change `bindings/tauri`
  or the API it wraps.
- Native bindings: `scripts/bindings.sh --check` (the committed glue matches
  the generator, and the bindings' tests pass), when you change
  `crates/frasil-uniffi` or the API it wraps.
- Mobile: `scripts/check-mobile.sh` (`frasil` for iOS on macOS with Xcode,
  and for Android with an NDK), when you change native dependencies or
  code gated on a target.
- Browser: `scripts/check-wasm.sh` (`frasil-wasm` on wasm32 in Node.js),
  `scripts/check-browser.sh` (`frasil`'s `browser` feature in headless
  Chromium, in a page and a worker),
  and `scripts/check-js.sh` (the npm package in Chromium and WebKit),
  then `pnpm lint`. pnpm's version is the `packageManager` field in
  `package.json`.
- Spec: from `docs/spec/reference`, run `python3 generate.py --check`
  (Python 3.12 or later, with the pinned requirements in a venv; see
  `docs/spec/reference/README.md`).

Tests marked `#[ignore]` are measurements or need an S3-compatible
service. Do not report checks you did not run as passing.

## Writing code

- Everything here is MIT. Source files carry no licence header: the root
  `LICENSE` covers the repository, and each package keeps a copy of it.
- Comments and docs explain the code as it is, and cite the spec by
  document and section title, for example "roster.md, 3.7 The resolution
  procedure". They do not mention who decided something, plans, review
  rounds, issue history, or other products.
- Prefer the public `frasil` API in examples and guides. Reach into
  `frasil::advanced` or the protocol crates only when the task needs to.
- Keep secrets in zeroizing types, compare them in constant time
  (`subtle`), and never log key material or plaintext.

## Writing documentation

Documentation is for people who build on Frasil or run a peer. It
describes what the code does now: the API, the behaviour, the limits, and
how to operate it.

- Leave out decision records, design history, migration notes from earlier
  implementations, and conversation with or about agents.
- Do not name other products or private repositories.
- When you change behaviour, update the matching guide in `docs/`, the
  crate docs, and `packages/frasil/README.md` for the browser surface.
- When you add a guide, list it in the README's Guides section.

## Commits and pull requests

- Work on a branch and open a pull request against `main`.
- Commit subjects use a conventional prefix with a scope, then a sentence
  about the behaviour, for example
  `fix(drive): a stale save stays a head and does not take the file's place`.
  Use `spec(...)` for specification changes.
- Keep one concern per PR. Spec, reference and vector changes go in the same
  PR as the code they drive. Dependency pins go in their own PR.
